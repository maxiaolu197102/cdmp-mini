关键性能瓶颈与已施行修复（原因 → 影响 → 现状）
LIKE 模式导致索引失效（主要 culprit）

原因：当 controller 构造的 pattern 允许或默认加入前导 %，MySQL/索引无法使用 B-Tree 前缀索引，导致全表扫描。
你已修复：buildLikePattern 现在会转义 _/%，并在用户没提供 % 时只追加尾部 %（即 prefix%），有很高概率能走索引。
风险/注意：若用户主动提供 %（比如 %@company.com），控制器会保留，仍会导致全表扫描——这是必然且合理的行为（用户要求任意子串匹配）。
N+1 Policy Count

原因：对每个 user 单独查询 policy count 导致 DB 额外查询次数随页大小线性增长。
你已修复：新增 CountByUsernames，将多个 username 聚合成一个 GROUP BY 查询并返回 map，service 填充 TotalPolicy。
效果：减少 DB 往返次数，大幅降低 p99 在 high concurrency 下的抖动。
COUNT(*)（全表聚合）在 list 中

原因：对全表做 COUNT(*) 在大表上昂贵，尤其在高并发时会阻塞 IO。
你已采取：在 list store 中移除 COUNT 查询（现在只返回 rows），需要时可通过 async/approximate/count cache 或单独接口提供 total。
注意：客户端若依赖 total，需提供替代方案（例如分页游标或近似总数）。
Producer 后端阻塞/降级

机制：enqueue 阻塞会触发 fallback 文件写入并由 compensator 重试，长时大量失败会导致磁盘堆积和 IO 压力。
可观测项：监控 fallback 文件数量、compensator 成功率、producer enqueue 时间分布。
